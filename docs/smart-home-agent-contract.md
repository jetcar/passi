# Passi Smart Home v1 — контракт для C:\repo\xiaomi-local-home

Расширение для облачного редактора расписаний описано отдельно:
[контракт ExchangeSchedule](smart-home-schedule-agent-contract.md). Оно включается
агентом явно, не меняет power.set и требует обновления локального адаптера.

Облачная реализация находится в этом репозитории; документ не означает, что она уже развёрнута.
Production не изменялся. Перед подключением потребуется отдельно согласованный выпуск облачной части.
Первоначальная облачная реализация не изменяла локальный проект. Расширение
2026-11-22 связывает этот контракт с каталогом нескольких локальных устройств.

## Задание для сессии локального сервера

Добавить фоновый исходящий агент к существующему ASP.NET Core / .NET 10 серверу.
Сохранить независимое локальное управление и существующие LAN-ограничения. При сбое облака
не блокировать запуск сервера, чтение устройства или локальные команды. Не публиковать локальный HTTP API,
не менять роутер/порты. Подключать зарегистрированные в своей LAN устройства с проверенным
драйвером; сейчас это розетки `chuangmi.plug.hmi206`. Неподдерживаемые модели, включая
Tuya/Midea, не объявлять управляемыми.
Использовать локальный сервис устройства напрямую, с его блокировкой операций и обратным чтением.
При тестировании использовать эмулятор; реальные устройства не переключать.

## Регистрация, секреты и отзыв

Каждый физический локальный сервер регистрируется как отдельный `homeId` со своим
токеном. Идентичность устройства в облаке — **пара `(homeId, deviceId)`**, а не один
`deviceId`. Совпадающие идентификаторы в разных домах не объединяются. В интерфейсе
выбирается сервер или «Все серверы»; команды всегда содержат выбранный `homeId`
в маршруте. Копирование credentials между домами заменит соединение старого агента,
а не добавит второй сервер.

Внутренний LAN `serverId` и облачный `homeId` имеют разные назначения: первый
принадлежит локальной регистрации, второй назначается Passi при регистрации сервера.
Добавление устройства на уже подключённом сервере не требует нового enrollment.

1. Войти существующим входом Passi как `admin@passi.cloud`, открыть `/smart-home`, добавить сервер.
   Облако находит подтверждённую существующую учётную запись в `Users`, проверяет сертификат из
   подписанного токена и один раз сохраняет `UserDb.Guid`. Повторное создание аккаунта с тем же email
   не переносит права. Клиентские email/userId/роли не используются для назначения владельца.
2. Страница один раз показывает `homeId`, `enrollmentSecret` и `expiresAt`. Код — 256 случайных бит,
   base64url без padding, 43 символа; срок 10 минут. Передать агенту локальным защищённым вводом,
   не через URL, аргументы командной строки, исходники или чат.
3. Агент делает HTTPS POST:

   ```http
   POST https://passi.cloud/passiapi/api/smarthome/agent/homes/{homeId}/enroll
   Content-Type: application/json

   {"enrollmentSecret":"<одноразовый код>"}
   ```

   Успех 200 (тело нельзя журналировать):

   ```json
   {"homeId":"<uuid>","token":"<43-символьный секрет>","expiresAt":"2027-02-19T12:00:00Z"}
   ```

   Срок токена 90 дней. Код атомарно погашается. Неверный, просроченный, уже погашенный код,
   код другого дома → 401 `invalid_enrollment`. Ограничение частоты → 429. Отсутствующий владелец → 403.
   Если ответ потерялся, нельзя восстановить токен из облака: создать новый код в интерфейсе и повторить
   регистрацию. Ответы `Cache-Control: no-store`.
4. Сохранить токен атомарно вне репозитория, с ограниченными правами пользователя службы:
   Windows — закрытый ACL/DPAPI при возможности; Linux — каталог 0700, файл 0600.
   Не отдавать его локальному UI/API, в диагностике маскировать заголовок Authorization и тела регистрации.
   Xiaomi/Tuya/Midea-ключи никогда не отправлять Passi.
5. Ротация: владелец нажимает «Новый код регистрации» для существующего дома; прежний токен сразу
   становится недействительным, команды закрываются, агент проходит шаги 2–4. Нет периода перекрытия.
   «Отозвать доступ» инвалидирует также непогашенный код. Для восстановления нужен новый код.
   Соединение переавторизуется при каждом Exchange; отозванный агент не сможет получить команды,
   опубликовать состояние или результат, даже если старый WebSocket ещё открыт.

Облако хранит только SHA-256 токена/кода, идентификатор владельца/дома, срок и поколение полномочий.
Токен агента не является пользовательским access token. Пользовательский токен не подходит к hub,
агентский — к пользовательским HTTP endpoint.

## Транспорт и аутентификация

- SignalR JSON protocol v1, только WebSocket: `wss://passi.cloud/passiapi/api/smarthome/agent/hub`.
- В .NET URL для `HubConnectionBuilder.WithUrl` начинается с `https://`; транспорт сам использует WSS.
- Обязателен `Authorization: Bearer <token>` в заголовке WebSocket upgrade. Никаких секретов в query.
  Query `access_token` отклоняется. HTTPS и стандартная проверка сертификата обязательны.
- `.NET Microsoft.AspNetCore.SignalR.Client`, `HttpTransportType.WebSockets`, `SkipNegotiation = true`.
  Пример настройки (token уже прочитан из закрытого локального хранилища):

  ```csharp
  var connection = new HubConnectionBuilder()
      .WithUrl("https://passi.cloud/passiapi/api/smarthome/agent/hub", options =>
      {
          options.Transports = HttpTransportType.WebSockets;
          options.SkipNegotiation = true;
          options.Headers["Authorization"] = "Bearer " + token;
      })
      .Build();
  ```

  Не включать автоматические повторы вызовов команд. При ротации пересоздать HubConnection с новым
  заголовком. Входящее управление дома/идентификатор владельца в URL или аргументах hub отсутствуют:
  дом выводится из проверенного токена. Не использовать браузерный SignalR-клиент для агента.
- Единственный прикладной метод: `InvokeAsync<ExchangeResponse>("Exchange", request, cancellationToken)`.
  Сервер не вызывает произвольные методы агента и не передаёт URL, HTTP-запросы или shell-команды.
- Вызов каждые 5 секунд, без параллельных Exchange. Каждый вызов отправляет полный список
  зарегистрированных устройств и состояние, затем получает команды. Heartbeat SignalR не заменяет Exchange.
- Максимальный размер сообщения 64 KiB, устройств 32, результатов за вызов 64.
  Максимум 10 домашних серверов. Строки id/name/model/errorCode не более 80 символов.
- Сервер онлайн, пока Exchange был не более 20 секунд назад; показания актуальны не более 30 секунд.
  При разрыве соединения статус меняется сразу после обнаружения разрыва, иначе — по истечении lease.

## Exchange: запрос

Все ключи JSON camelCase; даты UTC ISO 8601; идентификаторы команд/homeId UUID.
Идентификатор устройства стабилен между перезапусками, не является секретом. Допустимы
`[A-Za-z0-9][A-Za-z0-9_.:-]*` длиной 1–80.

```json
{
  "snapshotAt":"2026-11-21T12:00:05Z",
  "devices":[
    {
      "id":"xiaomi-plug-454002390",
      "name":"Xiaomi-розетка",
      "model":"chuangmi.plug.hmi206",
      "online":true,
      "capabilities":["power.read","temperature.read","power.set"],
      "power":true,
      "temperatureCelsius":38,
      "updatedAt":"2026-11-21T12:00:04Z"
    }
  ],
  "results":[]
}
```

- `snapshotAt` — время формирования сообщения, не время чтения розетки. В текущем соединении
  снимки не могут идти назад, быть старше 30 секунд или более чем на 5 секунд впереди времени Passi.
  Первый снимок формируется после подключения. Часы агента должны быть синхронизированы.
- `updatedAt` — время фактического чтения данного устройства, не искусственно обновляемый heartbeat.
  Нельзя повторно объявлять кэш новыми измерениями. Показания по устройству не должны идти назад.
- При отсутствии подтверждённой связи с устройством передавать `online:false`; неизвестные `power`
  и `temperatureCelsius` — `null`. `online:false` означает отсутствие подтверждённой доступности,
  а не доказанный физический выход устройства из строя. При сохранении старых показаний сохранять их время.
- Только указанные три capability. Для `power.set` нужен также `power.read` и свежая подтверждённая
  доступность/состояние. Температура Xiaomi — внутренняя температура, **не температура воздуха**.
- Список полный: отсутствующее устройство считается удалённым из доступного реестра. Не посылать
  IP/MAC, сетевые адреса, токены miIO, произвольные metadata/методы и ещё не интегрированные устройства.

## Exchange: ответ и исполнение

```json
{
  "serverTime":"2026-11-21T12:00:05Z",
  "commands":[
    {
      "id":"94df42c0-eaba-46b4-a747-887919967ff7",
      "homeId":"b0af5a58-80db-4c46-a8ea-0233b080dd30",
      "deviceId":"xiaomi-plug-454002390",
      "operation":"power.set",
      "on":false,
      "createdAt":"2026-11-21T12:00:02Z",
      "expiresAt":"2026-11-21T12:00:32Z",
      "status":"sent",
      "sentAt":"2026-11-21T12:00:05Z",
      "completedAt":null,
      "errorCode":null
    }
  ]
}
```

Срок команды — 30 секунд от принятия Passi. Облако атомарно записывает `sent` до ответа;
после потери ответа эта команда не придёт заново. Это at-most-once доставка, не гарантия выполнения.
На устройство одновременно допускается одна ожидающая/отправленная команда.

Обязанности агента:

1. Проверить homeId, зарегистрированный deviceId, точное `operation == "power.set"`, boolean `on` и срок.
   Никакого `toggle`: только явное желаемое состояние. До фактического обращения к устройству ещё раз
   проверить deadline; если оно занято, не накапливать очередь за пределами срока.
2. **До исполнения** надёжно записать commandId как полученный в локальный журнал дедупликации.
   При ошибке записи не исполнять. Один commandId никогда не исполнять дважды, включая рестарт агента.
   При рестарте запись без подтверждённого результата означает `unknown`, повтор запрещён.
3. Выполнить одну локальную операцию с существующей блокировкой и ограничением времени, затем
   запросить фактическое состояние. Не повторять miIO-переключение при таймауте/неясном результате.
   Не удерживать Exchange на время управления: следующий цикл отправит результат после завершения задачи.
4. Следующим Exchange отправить результат и снимок с подтверждённым обратным чтением:

   ```json
   {
     "commandId":"94df42c0-eaba-46b4-a747-887919967ff7",
     "status":"confirmed",
     "power":false,
     "observedAt":"2026-11-21T12:00:06Z",
     "errorCode":null
   }
   ```

   Допустимые результаты: `confirmed`, `failed`, `unknown`. `confirmed` требует обратного чтения
   после доставки, соответствующего `on`, и согласованного снимка устройства в том же Exchange.
   `failed` — достоверно отклонённая операция/известное несовпадение состояния. `unknown` — таймаут,
   отмена после отправки, обрыв или отсутствие надёжного обратного чтения. В неизвестном результате
   `power`/`observedAt` могут быть null. `errorCode` — короткий код, например `device_timeout`,
   `device_busy`, `readback_mismatch`; не exception text, токен или локальный адрес.
5. Успешный ответ Exchange означает, что результаты сохранены. Допустимо снова передать подтверждение
   в **том же соединении**, если ответ потерялся: завершённые записи не изменяются. Само действие не повторять.
   После reconnect старые результаты не отправлять; облако сохраняет их как unknown/expired, новое
   фактическое состояние приходит отдельным снимком. Результат после deadline не превращает unknown в успех.

Статусы интерфейса: `queued` — ожидает следующего Exchange; `sent` — облако передало/попыталось
передать, ещё не подтверждено; `confirmed` — согласованное обратное чтение; `failed` — ошибка;
`expired` — не доставлялась до разрыва/срока; `unknown` — была отмечена sent, подтверждение не получено.
Облако не повторяет queued-команды после reconnect и никогда повторно не доставляет sent.

## Ошибки и reconnect

HTTP возвращает `{ "error": "code" }` для ошибок домена; ошибки схемы JSON — стандартный ProblemDetails.
401 — неверные/истёкшие credentials; 403 — владелец не разрешён; 404 — дом/команда не найдены;
409 — конфликт состояния; 400 — неверные данные; 429 — превышение лимита. Тело может отсутствовать
при отказе middleware/authentication. Не зависеть от текста framework exceptions.

Hub выдаёт SignalR invocation error с кодом: `invalid_agent`, `forbidden`, `connection_replaced`,
`invalid_or_stale_snapshot`, `invalid_devices`, `invalid_device`, `invalid_result`, `duplicate_result`,
`unknown_command`, `command_connection_mismatch`. При 401/403 сервер закрывает соединение.
Неверная схема JSON/слишком большое сообщение может привести к стандартной ошибке SignalR/закрытию.

- Сетевой сбой: reconnect с jitter и задержками примерно 1, 2, 5, 10, 30 секунд, максимум 30–60 секунд.
  Никакого busy loop. Первое подключение тоже может не состояться — локальный сервер продолжает работать.
- На новый connectionId отправлять свежий полный снимок, пустой `results`; не переносить команды
  предыдущего соединения в очередь. Новый connectionId заменяет старый, в том числе при двух процессах
  с одним токеном. Старый получает `connection_replaced` и должен остановиться, не бороться за соединение.
- 401/403/отзыв/истечение токена: остановить автоматические попытки с этим секретом, показать локально
  «нужна регистрация». Не печатать credential. После защищённого ввода нового токена подключиться снова.
- Ошибки снимка: исправить часы/схему/показания, не «исправлять» updatedAt старого измерения на текущее.
  Ошибка вызова означает, что весь Exchange отклонён; не считать отправленные результаты принятыми.
- Прерывание до/после исполнения имеет неопределённую границу: локальный журнал не должен автоматически
  перезапускать действие. Заново читать состояние можно. Новое переключение требует новой команды владельца.

## HTTP интерфейса (не для агента)

WebApp BFF `/api/smarthome` использует cookie существующего входа и сохранённый access token.
WebAPI prefix `/passiapi/api/smarthome` проверяет подписанный OpenIDC access token для `ClientId` WebApp
и GUID владельца на каждом запросе. Агенту этот пользовательский токен передавать нельзя.

| Метод | Относительный путь | Тело / ответ |
|---|---|---|
| GET | `/access` | `{allowed:true}` либо 401/403 |
| GET | `` | `{serverTime,homes:[{id,name,online,lastSeenAt,snapshotAt,stale,devices,commands}]}` |
| GET | `/csrf` (только BFF) | `{token}` для заголовка `RequestVerificationToken` |
| POST | `/homes` | `{name}` → EnrollmentDto |
| POST | `/homes/{homeId}/enrollment` | `{}` → новый EnrollmentDto, старый токен отозван |
| POST | `/homes/{homeId}/revoke` | `{}` → 204 |
| POST | `/homes/{homeId}/devices/{deviceId}/power` | `{commandId:"uuid",on:true/false}` → CommandDto |

Повтор того же commandId с тем же домом/устройством/on возвращает прежнюю запись, не новую команду.
Иной payload с тем же id → 409 `command_id_conflict`. Отсутствующий `on` → 400, не выключение по умолчанию.
В dashboard последние 100 команд на дом; durable записи id не удаляются автоматически.

## Проверки локальной реализации перед подключением

Эмулятор: повтор commandId до/после рестарта; просроченная команда; потеря ответа Exchange;
разрыв до отправки/после miIO/до readback; несовпадающее readback; занятое устройство; отключённое облако;
старая дата измерения; неверный/отозванный токен; токен другого дома; ротация. Убедиться, что LAN работает
без Passi, а ни одно неизвестное переключение не повторено. Секреты отсутствуют в URL/логах/API/репозитории.

## Перед будущим выпуском облака

Накатить добавочную миграцию `20261121182804_smart_home_cloud` через существующий процесс миграций.
Сохранить данные SmartHomeOwners при любых операциях обслуживания: это неизменяемая привязка владельца.
Нужны существующие настройки `IdentityUrlBase` (issuer) и `ClientId` (именно WebApp, не PassiClientId).
WebApp обращается к `${PublicUrlBase ?? IdentityUrlBase}/passiapi`; необязательный
`SmartHomeApiBaseUrl` заменяет этот адрес и должен быть HTTPS с доверенным сертификатом.
Добавлена узкая маршрутизация `/api/smarthome` в HAProxy; `/passiapi` использует существующий backend.
Сохранять WebSocket upgrade и TLS. Платный backplane не нужен: Exchange забирает команды из PostgreSQL.

На внутреннем HTTP-переходе HAProxy → WebAPI заголовки `X-Forwarded-Proto` и `X-Forwarded-For` принимаются только
на `/api/smarthome` и только от точных IP доверенного прокси. По умолчанию адреса разрешаются
из Docker-имени `haproxy`; необязательный `SmartHomeTrustedProxyHost` заменяет это имя.
Для другой инфраструктуры `SmartHomeTrustedProxyAddresses` задаёт список буквальных IPv4/IPv6
через запятую и полностью заменяет DNS (например, `192.0.2.10,2001:db8::10`; использовать реальные
адреса своего прокси). CIDR/подсети не принимаются. DNS ограничен двумя секундами, результат
кэшируется на 30 секунд; ошибка DNS или неверный список запрещает forwarding.
Прокси обязан перезаписывать `X-Forwarded-Proto` фактической внешней схемой и дописывать фактический
адрес клиента справа в `X-Forwarded-For` (существующий `option forwardfor` в HAProxy).
Доверяется только последний переход: левые значения клиента игнорируются, ограничение регистрации
считается отдельно для каждого фактического IP клиента. Настройки остальных маршрутов не изменены.
