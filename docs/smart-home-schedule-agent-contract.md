# Расписания питания: расширение агента Passi, версия 1

Это задание для сессии `C:\repo\xiaomi-local-home`. Облачный редактор реализуется
в Passi отдельно; локальный адаптер в этой сессии не изменяется. Не объявляйте
поддержку, пока локальное хранилище и исполнитель не отвечают требованиям ниже.
Облачный выпуск и локальный выпуск требуется выполнить отдельно.

## Подключение и совместимость

Используется существующее исходящее TLS/SignalR-соединение и отдельный токен дома:
`https://passi.cloud/passiapi/api/smarthome/agent/hub`. Аутентификация — только
`Authorization: Bearer ...`, без query, новых портов, локального HTTP-прокси и
передачи Xiaomi/Tuya/Midea-ключей. Регистрация и отзыв из [основного контракта](smart-home-agent-contract.md)
не меняются. Один физический сервер — один homeId; устройства изолированы парой
`(homeId, deviceId)`.

Продолжайте `Exchange` каждые 5 секунд с обычным полным каталогом и результатами
`power.set`. Этот метод никогда не доставляет команды расписаний.
После успешного Exchange последовательно вызывайте `ExchangeSchedule` для каждой
поддерживаемой розетки. Разделение сохраняет предел 64 KiB на одно SignalR-сообщение
даже при нескольких устройствах. Размер проверять вместе с invocation-envelope.
Часы синхронизировать; один вызов на соединение одновременно.

`ExchangeSchedule` не продлевает свежесть каталога и не заменяет `Exchange`.
Первый валидный свежий снимок явным образом объявляет поддержку расписания конкретного
устройства. Старый агент без вызова получает только power.set. Устройство должно
уже присутствовать в каталоге этого дома с power.read и power.set. Не экспортировать
термостатный формат этим методом: v1 описывает только расписание bool-питания.

## Сообщение агента

```json
{
  "protocolVersion": 1,
  "deviceId": "xiaomi-plug-123",
  "snapshotAt": "2026-11-24T10:00:00Z",
  "configuration": {
    "version": 7,
    "deviceId": "xiaomi-plug-123",
    "enabled": true,
    "timeZone": "Europe/Tallinn",
    "outsidePower": false,
    "intervals": [
      {
        "id": "4b5accc4-d9c9-435e-b454-95e241b6a455",
        "name": "Утро", "enabled": true,
        "days": [1,2,3,4,5], "start": "06:00", "end": "09:00", "on": true
      }
    ]
  },
  "runtime": {
    "revision": 12,
    "state": "manual",
    "desiredPower": true, "actualPower": false,
    "checkedAt": "2026-11-24T09:59:55Z",
    "nextCheckAt": "2026-11-24T10:00:25Z",
    "nextBoundary": "2026-11-25T04:00:00Z",
    "manualActive": true,
    "manualUntil": "2026-11-25T04:00:00Z",
    "error": null
  },
  "results": []
}
```

`snapshotAt` — время получения согласованного снимка локального хранилища; не время
измерения устройства. `checkedAt` не обновлять при чтении кэша. Неизвестное физическое
состояние остаётся null. Конфигурация и runtime должны читаться под одной блокировкой.
Снимок не старше 30 секунд, не более 5 секунд в будущем и не раньше соединения.
Версии не уменьшаются; одинаковая версия не допускает изменённого содержимого.
Идентификатор устройства должен оставаться устойчивым между соединениями. Passi
сохраняет версии до 128 когда-либо объявленных устройств одного дома, даже после их
исчезновения из текущего каталога. Повторное добавление того же ID не обнуляет версии.
Новый 129-й ID отклоняется с `schedule_cache_limit`; это требует явного решения владельца,
а не автоматического создания нового дома или смены ID агентом.

Версии — целые 0..9007199254740991. Увеличивать максимальное значение нельзя.
Не более 64 интервалов: уникальные UUID, имя до 80 символов, уникальные дни ISO 1..7,
время HH:mm. 24:00 допустимо только как конец; равное начало/конец запрещено.
Конец раньше начала означает ночь с переходом на следующий день, включая воскресенье.
Противоречивые пересечения активных интервалов запрещены. `outsidePower=null` означает
не управлять вне интервалов; интервалы `on=false` сохраняют выключение, не заменять их
включением. Часовой пояс — существующий IANA ID; переходы DST исполняются локально.

## Ответ и операции

Ответ: `{serverTime, commands: [...]}`, максимум одна команда для этого устройства.
Общие поля команды: `id`, `homeId`, `deviceId`, `operation`, `createdAt`, `expiresAt`,
`sentAt`, `status`. Срок — 30 секунд. Совместимое поле `on` не относится к расписанию.

`schedule.replace`: `expectedVersion`, `configuration`. configuration.version равна
expectedVersion. Агент проверяет срок, адресата, формат и текущую локальную версию;
атомарно сохраняет конфигурацию с version+1 и результат по commandId. Новая конфигурация
пересчитывает окончание активной ручной паузы по существующим правилам планировщика.

`schedule.resume`: `expectedVersion`, `expectedRuntimeRevision`. Агент проверяет обе
версии, снимает именно эту ручную паузу и увеличивает runtime.revision ровно на 1,
не меняя версию конфигурации. Снятие паузы не является физическим подтверждением питания.

**Требуется обновление локального хранилища.** Текущий локальный `ResumeAsync(version)`
не реализует этот контракт. Добавьте durable runtime.revision и журнал commandId
в транзакцию/атомарную запись под тем же gate, что SaveAsync, ResumeAsync, ManualAsync
и шаг исполнителя. Revision увеличивается при новой/повторной ручной команде,
автоматическом истечении паузы, её снятии, изменении срока при сохранении расписания.
Не вычисляйте revision из времени снимка или чтения GET. Не считайте повтор ручной
команды тем же состоянием: он также должен защититься от уже ожидающего resume.

До исполнения проверьте commandId в устойчивом журнале. Тот же ID и намерение возвращает
сохранённый результат без повторного действия; иное содержимое — конфликт. Между
проверкой дедлайна/версии и записью не должно быть окна для ручного действия.
Авария между сохранением и ответом не должна приводить к повторному resume после старта.

## Подтверждение и ошибки

Следующий ExchangeSchedule передаёт обновлённый снимок и до одного результата:

```json
{
  "commandId": "7072c147-e75d-4ef9-baa7-ec9f45ed597c",
  "status": "confirmed",
  "observedAt": "2026-11-24T10:00:06Z",
  "appliedVersion": 8,
  "runtimeRevision": 12,
  "errorCode": null
}
```

confirmed означает, что локальный сервер сохранил настройки/ручной режим и перечитал
их. Для replace конфигурация должна совпасть с командой и иметь expectedVersion+1.
Для resume: configuration.version=expectedVersion, runtime.revision=
expectedRuntimeRevision+1, manualActive=false. `observedAt` не раньше sentAt и
не позже snapshotAt. Физическое питание проверяется отдельно обычным Exchange.

`failed` — доказанный отказ до применения (например, version_conflict,
runtime_revision_conflict, invalid_schedule, storage_unavailable). `unknown` — нельзя
доказать, применилось ли изменение. Не возвращайте confirmed по факту получения.
При конфликте передайте актуальный снимок; облако не перезаписывает его черновиком.

Общие auth/connection_replaced/clock/size ограничения прежние. Для ошибок валидации
не повторяйте ошибочный payload бесконечно: исправьте адаптер/часы. При invalid_agent
остановите подключение до новой регистрации. Не помещайте секреты, адреса или
произвольные сообщения исключений в errorCode.

Ошибки `ExchangeSchedule` возвращаются как SignalR completion error с кодом:

| Код | Действие агента |
| --- | --- |
| `unsupported_schedule_protocol` | Использовать protocolVersion=1; не объявлять неподдерживаемый формат. |
| `unsupported_device_operation` | Сначала передать зарегистрированное устройство с power.read/power.set в Exchange. |
| `home_offline_or_stale` | Обновить обычный Exchange; расписание не заменяет heartbeat каталога. |
| `schedule_cache_limit` | Достигнут предел 128 исторических устройств с расписаниями; сообщить владельцу, не обходить сменой homeId. |
| `invalid_or_stale_snapshot` | Получить новый согласованный снимок, проверить часы. |
| `invalid_schedule`, `conflicting_schedule_intervals`, `invalid_schedule_runtime`, `invalid_result` | Исправить формат; не повторять тот же payload. |
| `stale_schedule_version`, `schedule_version_content_conflict`, `runtime_revision_conflict` | Перечитать устойчивое локальное хранилище; не обнулять счётчики после перезапуска. |
| `unknown_command`, `command_operation_mismatch`, `command_connection_mismatch` | Не подтверждать чужую команду или команду предыдущего соединения. |

Результат физического чтения `runtime.actualPower` требует `checkedAt`; runtime.error,
как и errorCode, содержит только короткий код без текста исключений. Неизвестные
поля входного расширения отклоняются: новые возможности требуют согласования контракта.

## HTTP редактора Passi

Существующая серверная owner-policy применяется к обоим новым POST-маршрутам:

- `/api/smarthome/homes/{homeId}/devices/{deviceId}/schedule`:
  `{commandId, expectedVersion, configuration}`.
- `/api/smarthome/homes/{homeId}/devices/{deviceId}/schedule/resume`:
  `{commandId, expectedVersion, expectedRuntimeRevision}`.

Браузер использует одноимённые маршруты BFF `/api/smarthome/...` с существующей сессией
и CSRF-токеном. Снимки доступны в `homes[].schedules[]` обычного dashboard, включая
`deviceId`, `snapshotAt`, `stale`, `configuration`, `runtime`. Успешный POST возвращает
CommandDto со статусом queued для новой команды; повтор того же ID с тем же намерением
возвращает прежний статус без нового исполнения. queued не подтверждает сохранение. Состояние команды
читается из dashboard. Ответы не кэшируются.

Конфликты возвращают HTTP 409 и `{error: code}`: `schedule_not_supported`,
`schedule_offline_or_stale`, `version_conflict`, `runtime_revision_conflict`,
`manual_override_not_active`, `command_in_progress`, `command_id_conflict`.
После конфликта пользователь перечитывает актуальное состояние. Транспортная ошибка
не разрешает повторить операцию с новым commandId автоматически.

## Обрыв и восстановление

После нового соединения сначала обычный Exchange, затем новые ExchangeSchedule.
Кэш Passi остаётся видимым, но stale до свежего объявления на новом соединении.
Queued команды истекают, sent становятся unknown; автоматической повторной доставки нет.
Просроченные команды не выполнять. После потери ответа сначала перечитайте локальную
конфигурацию и журнал. Позднее подтверждение не меняет terminal unknown в Passi.
Возможны новые явные действия пользователя только по актуальным версиям.

При недоступности Passi локальные расписания продолжаются без изменений. Не исполняйте
накопленные переходы после восстановления WAN и не создавайте облачный таймер.

## Проверка локального адаптера

На эмуляторе: v1 совместимость, два дома с одинаковым deviceId, отсутствие capability,
CRUD конфигурации через replace, конфликт локального и облачного изменения, новая
ручная команда перед resume, повтор commandId, crash после записи до ответа,
отключение WAN и повторное соединение, просрочка, unknown, DST и ночные интервалы.
Не сохраняйте активные расписания и не переключайте реальные устройства ради тестов.
